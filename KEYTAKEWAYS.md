# Key Takeaways: MT5 Remote Backtest Architecture

## File-Based IPC Over Direct Networking

**Pattern:** Use cloud sync (OneDrive) instead of sockets, SSH, or REST APIs.

**Why:** No firewall config, no auth tokens, no network reliability concerns. Works across versions and networks. Local machine and VPS just need sync access.

**Trade-off:** Latency = sync interval (usually seconds). Not real-time, but fine for batch jobs.

**When to use:** Batch processing, not event-driven. When machines don't need to talk directly.

## State Machine via Atomic Folder Moves

**Pattern:**
```
Queue → Processing → Processed
```

**Why:** Atomic move prevents double-processing even if script crashes mid-execution. Each file has exactly one state at any time.

**Implementation:** `shutil.move()` moves file, then checks existence before proceeding. If crash after move but before completion, file stays in Processing on restart — detect and resume.

**When to use:** Any job queue where reliability matters. Avoids complex lock files or database tracking.

## INI Injection for External Application Control

**Pattern:** Generate config file → Pass path via CLI flag → External app reads and executes.

```python
subprocess.run([MT5_TERMINAL_PATH, f"/config:{os.path.join(PROCESSING_DIR, 'mt5.ini')}"])
```

**Why:** No API needed. Works with any app that accepts config file path. Separates concerns — your script owns logic, MT5 owns execution.

**Trade-off:** You're coupled to MT5's config format. If MT5 updates, parser might break.

## Two-Pass Backtesting with Separate Runs

**Pattern:** One date range → Two sequential MT5 invocations.

**Why:** MT5 tester runs one config per session. To get both backtest and forward metrics from same .set file, split into two time ranges and run twice.

**Lesson:** External tools often have CLI limitations. Work around by orchestrating multiple invocations with different parameters.

## Centralized Dynamic Config with Reset Flags

**Pattern:**
```json
{
  "Symbol": "NAS100ft.s",
  "ClearResults": true
}
```

**Why:** Allows one-shot commands (clear results) without editing script. Config file syncs via OneDrive — change once, effective everywhere.

**Lesson:** Add `ClearResults` type flags for operations you might need once. Avoids script edits for infrequent tasks.

## HTML Report Parsing for Structured Data

**Pattern:** Regex extraction from HTML reports generated by closed-source app.

**Why:** No SDK/API available. MT5 outputs HTML reports, so parse what you can get.

**Implementation:**
```python
m_profit = re.search(r"Total Net Profit.*?<td[^>]*>(.*?)</td>", content, re.IGNORECASE | re.DOTALL)
```

**Lesson:** Regex is fragile but zero-dependency. Use when you can't control source format. Document expected patterns. Add fallback calculations (e.g., WinRate from Trades count if percentage not in report).

## Polling Loop for Job Discovery

**Pattern:**
```python
while True:
    queue_files = glob.glob(os.path.join(QUEUE_DIR, "*.set"))
    if not queue_files:
        time.sleep(2)
        continue
```

**Why:** Simple, reliable, no event system needed. Works with file-based IPC.

**Trade-off:** Latency = sleep interval. 2 seconds acceptable for batch jobs. For faster response, use file system watchers (inotify on Linux, ReadDirectoryChangesW on Windows).

## Subprocess Execution with Silent Failure Mode

**Pattern:**
```python
subprocess.run([MT5_TERMINAL_PATH, f"/config:{path}"], check=False)
```

**Why:** MT5 runs headless, no exit code to parse. `check=False` lets script continue to check for output files instead.

**Lesson:** Don't rely on return codes when external app is opaque. Check artifacts (HTML report exists) as success signal, not exit code.

## CSV Append for Results Logging

**Pattern:** Open with `'a'`, write row, close. Single file per run.

**Why:** Simple, diff-friendly, no DB needed. Append-only scales well for thousands of runs.

**Trade-off:** No transactions, no rollback. If crash mid-write, CSV can be corrupt. Mitigation: write to temp file, rename on complete (atomic rename on Windows).

## When NOT to Use This Architecture

- **Real-time requirements** → Use WebSocket or event-based system
- **High throughput** → Batch jobs okay, but consider queue system (Redis, RabbitMQ)
- **Multi-process coordination** → Needs locking mechanism, not just folders
- **Mission-critical reliability** → Add watchdog, restart logic, notifications

## Summary

This system favors simplicity and reliability over sophistication. File sync + folder state machine + polling + subprocess = works reliably on RDP with minimal maintenance.
